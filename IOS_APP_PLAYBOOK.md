# iOS app playbook

A reusable guide for building iOS apps with paid AI features, subscriptions and one-time purchases. Started 7 October 2026 alongside [the Nifty Outfit Nook build plan](SWIFT_BUILD_PLAN.md).

Nifty Outfit Nook is the first project built with it, and building that app is also how this playbook gets written. The playbook is a deliverable in its own right, as important as the app. Its aim is apps that are reliable, compliant with Apple's rules, safe for users and the developer, and cheap to run.

The rule for this file: only write down what we actually did and checked. Each section fills in as the matching phase finishes. Lessons specific to Nifty Outfit Nook stay in the build plan's progress log.

## Required standards

- **[SECURITY_STANDARD.md](SECURITY_STANDARD.md)** is the required security baseline for every app built with this playbook. It isn't optional and isn't a later phase.

## 0. Repositories and branching
Separate repos for design and planning, the app, and the private backend. Git Flow in the app and backend repos (`main`, `develop`, `feature/*`, `release/*`, `hotfix/*`), with protected branches, required CI and no stacked feature branches. The decided model is in [SWIFT_BUILD_PLAN.md](SWIFT_BUILD_PLAN.md#repositories-and-branching); lessons go here once it's in use. *(Phase 1b)*

Verified 14 October 2026 on a public personal repo (Nifty Outfit Nook, Phase 1b):
- **Order matters: CI first, rulesets second.** Merge the PR that adds CI, then create the ruleset, so the required checks already exist by name. A required check is the job's `name`. Pin it to GitHub Actions with `integration_id: 15368` so a commit status from elsewhere can't satisfy it.
- **One ruleset can cover `main` and `develop`** (`refs/heads/main` and `refs/heads/develop` in `include`). With `bypass_actors: []` the API reports `current_user_can_bypass: "never"`, administrators included. Rules used: `deletion`, `non_fast_forward`, `required_linear_history`, `required_signatures`, `pull_request` (0 approvals for a one-person repo, `allowed_merge_methods: ["squash"]`) and `required_status_checks`.
- **Test it from a throwaway clone.** `git commit --allow-empty` on `develop` and push: GitHub rejects it and lists every rule broken (pull request, status checks, signatures). Deleting the branch is rejected too. `gh api repos/{o}/{r}/rulesets/rule-suites` shows each evaluation afterwards.
- **`gh pr merge` stops working under `required_signatures` when your commits are unsigned.** It refuses on the client side ("the base branch policy prohibits the merge") because GraphQL reports the PR as `BLOCKED`, even with every check green. `gh api -X PUT repos/{o}/{r}/pulls/<n>/merge -f merge_method=squash` merges it as a normal user: GitHub signs the squash commit and the ruleset evaluation passes. Wrap that in a script that runs `gh pr checks <n> --watch` first. Signing commits locally probably also fixes it, but we haven't tried that.
- **Squash-only promotions to `main` need a promotion branch.** Verified 14 October 2026 at the first milestone (Nifty Outfit Nook, end of Phase 3). With `required_linear_history` and squash as the only merge method, promoting `develop` into `main` leaves `main` with one squash commit that `develop` never gets, so the two share no history past the first commit. The first promotion PR straight from `develop` merged cleanly because `main` was still the first commit. A later one wouldn't: simulating one more `develop` commit, `git merge-tree --write-tree origin/main <that commit>` reported a conflict in the edited file. A sync PR from `main` back into `develop` doesn't help, since it's squashed too. What works: `git commit-tree <develop's tree> -p origin/main`, push it as a `promote/...` branch and open the PR from there; the diff is exactly what changed since the last promotion. Script it, and point the agent notes at the script.
- **Repo settings that aren't files**, all set with `gh api`: squash merge only and delete branches on merge (`PATCH /repos/{o}/{r}`); secret scanning and push protection (`security_and_analysis` in the same PATCH; non-provider patterns and validity checks stay off on a free personal repo); `PUT .../vulnerability-alerts`, `.../automated-security-fixes` and `.../private-vulnerability-reporting`; a read-only token that can't approve PRs (`PUT .../actions/permissions/workflow`); only GitHub-owned actions, with SHA pinning enforced (`PUT .../actions/permissions` with `allowed_actions=selected` and `sha_pinning_required=true`, then `.../selected-actions` with `github_owned_allowed=true`); and approval for every outside contributor's workflow run (`PUT .../actions/permissions/fork-pr-contributor-approval` with `all_external_contributors`). List them in the README, since nobody will find them in the code.

## 1. Project setup
Project generation, package layout, configurations, language mode, lint and format. *(Phase 0a, 1a)*

Verified 13 October 2026 with Xcode 26.6 (Nifty Outfit Nook, Phase 1a):
- **A hand-written project file works.** With `objectVersion = 77`, each source folder is one `PBXFileSystemSynchronizedRootGroup` listed in the target's `fileSystemSynchronizedGroups`, and the Sources and Resources build phases stay empty. Put build settings in xcconfig files (`baseConfigurationReference`) so the project file stays small. Check it with `xcodebuild -list` and a real build.
- **Add a local package as a folder reference, not an `XCLocalSwiftPackageReference`.** Use a `PBXFileReference` with `lastKnownFileType = wrapper` and `path = Packages/<Name>`, and product dependencies without a `package` field. With `XCLocalSwiftPackageReference`, Xcode built the package with `-suppress-warnings` (which clashes with warnings-as-errors) and silently skipped the package's test targets in the scheme and test plan.
- **Run package tests through a test plan.** Each package test target appears as `{"containerPath": "container:Packages/<Name>", "identifier": "<TestTarget>", "name": "<TestTarget>"}`. The app scheme's test action then runs the package tests and the UI tests together on a simulator, which matters when the package is iOS-only and `swift test` can't run on the Mac.
- **Warnings as errors:** set `SWIFT_TREAT_WARNINGS_AS_ERRORS = YES` in the project xcconfig and `.treatAllWarnings(as: .error)` (Swift 6.2 tools) in `Package.swift`. Don't pass it on the `xcodebuild` command line, because that reaches package targets too and can clash with `-suppress-warnings`. Prove it works by adding a warning on purpose.
- **Data Protection** goes in the entitlements file as `com.apple.developer.default-data-protection = NSFileProtectionComplete`. A simulator build shows it in the `*-Simulated.xcent` file under DerivedData, not in `codesign -d --entitlements`.
- With `defaultIsolation(MainActor.self)` on a module, its test target also needs `@MainActor` on tests that touch that module's types, or `#expect` fails to compile.

### CI for an iOS app on GitHub Actions

Verified 14 October 2026 (Nifty Outfit Nook, Phase 1b):
- **Check the runner image before picking a label.** The image READMEs in `actions/runner-images` (`images/macos/macos-26-arm64-Readme.md`) list each Xcode and simulator runtime. `macos-26` had Xcode 26.0.1 to 26.6 and iOS 26.2, 26.4 and 26.5 simulators. Select Xcode by path (`sudo xcode-select --switch /Applications/Xcode_26.6.app`) instead of trusting the default, and choose the simulator at run time from `xcrun simctl list devices available --json`, because device names and runtimes differ between the image and a dev Mac.
- **Pin actions by SHA.** `gh api repos/<owner>/<repo>/git/ref/tags/<tag>` gives the commit SHA when `object.type` is `commit`, as it was for every tag we used. An annotated tag returns `tag` instead, and its `object.url` leads to the commit. Write `uses: actions/checkout@<sha> # v7.0.1` so Dependabot can still update it.
- **gitleaks without a third-party action:** download the release tarball, check it against a SHA-256 copied from the release's checksums file into the workflow, and run `gitleaks git --redact .` after a `fetch-depth: 0` checkout to scan the whole history. It takes about 7 seconds on `ubuntu-latest`.
- **Workflow defaults:** top-level `permissions: contents: read`, `persist-credentials: false` on checkout, a timeout on each job, and a concurrency group that cancels superseded runs only for pull requests (`cancel-in-progress: ${{ github.event_name == 'pull_request' }}`). Upload the `.xcresult` only `if: failure()`.
- **Timing:** swift-format lint about 10 seconds, gitleaks about 7 seconds, and a Release build plus package and UI tests about 5 to 7 minutes on `macos-26` at first, most of it the first UI test launching the simulator. It grew with the UI tests (see the next points).
- **When the build-and-test job gets slow, read the step times before changing anything** (verified 14 October 2026, Phase 5b). Our 18-minute job was 1.7 minutes of Release build, about 1 of Debug build, 1 of simulator boot, 2 of package tests and 10 of UI tests run one after another; the hosted runner takes 0.3 to 1 second per UI query and sometimes over a minute for one launch. Splitting the UI tests into parallel jobs brought the check to about 12 minutes; it's now set by the slowest part.
- **Keep the required check's name with an aggregator job.** Give the parallel jobs new names and make the required one (`build-and-test`) a small `ubuntu-latest` job with `needs:` on all of them, `if: always()`, and a step that fails unless every `needs.<job>.result` is `success`. Without `always()` it is skipped when a job fails, and GitHub counts a skipped required check as passed. The ruleset doesn't change.
- **Split UI tests by class, with a catch-all part.** `xcodebuild test-without-building -only-testing:UITests -skip-testing:UITests/ClassA -skip-testing:UITests/ClassB` runs every other class, so a new class can't be left out. Build once per job with `build-for-testing`, and pass the selection through the test script.
- **Each UI job on a hosted macOS runner costs about 6 minutes before its first test passes**: setup, the build, a cold simulator boot and the first app launch (that first UI test alone took 2 to 3 minutes). More parts give less back each time. Booting the simulator in the background during the build made the build take 9 minutes instead of 1 to 2.5, and waiting for a full boot with `simctl bootstatus -b` took 2 to 4 minutes; letting `xcodebuild` boot it was faster than both. The free plan runs five macOS jobs at once, so count runners when adding parts.
- **Give UI test waits room on CI.** A back tap that lands in under a second locally once took more than 5 seconds to show the previous screen on the runner. A 15-second wait costs nothing when the condition is met early.
- **Wait for the pushed screen to go, not only for the one under it** (verified 15 October 2026, Phase 11). After Back, the previous screen's navigation bar exists while the pushed screen is still sliding away, so a test that tapped the next control as soon as it appeared lost the tap on a slow runner. A shared `goBack(from:to:)` that waits for the pushed bar to stop existing, and a sheet button helper that taps once more only if the button is still there, ended the Home flakes. Don't swipe down on an open sheet to scroll it; that can start closing it.
- **Retry UI tests once on CI only, for simulator launch failures.** "Timed out while launching application via Xcode" and "Failed to get launch progress" lost a test twice in about 25 runs, and no wait inside a test catches them. `xcodebuild test-without-building … -retry-tests-on-failure -test-iterations 2` works with a pre-built bundle; the log shows "(Iteration 1 of 2)" and a test that fails twice still fails the job. Keep it out of local runs and package tests, and say in the workflow why it's there.
- **Balance UI parts from the test log, by class, and keep a catch-all** (verified 15 October 2026, Phase 12b). Each `Test Case '-[Class test]' passed (N seconds)` line in the job log gives a class's time; summing them per part showed one part held 22 of 38 minutes. Regrouping the classes into four parts of about equal time, with the catch-all part still skipping only the named classes, took the required check from about 29 to 20 minutes with no new runners. Hosted-runner times for the same class swung by up to two times between runs, so record the numbers in the workflow and rebalance when one part drifts well past the others.
- **Spare time on a non-UI job isn't free UI time** (verified 15 October 2026, Phase 15b). Running a UI class after the package tests, on the same runner and simulator, rebuilt in 18 to 27 seconds, but the first UI launch there still took 3 to 7 minutes, and that job became the longest (22 to 26 minutes). Moving the iPad tests to a part of their own and rebalancing took the check from 25 to 30 minutes to 24 to 26, not to 20: with all five macOS runners busy and the same class running up to 1.5 times slower between runs, measure two or three runs before believing a new split.
- **The sixth macOS job may be the one that waits.** With six macOS jobs and five runners, GitHub sometimes started the five test jobs first and left `swift-format` queued for 14 minutes. The required checks still finished, but a quick check can arrive last.
- **Let UI tests open a long debug page at the part they need.** Tests that swiped through a whole component catalog to reach one section took 45 to 140 seconds each on CI. A Debug-only launch argument that shows one catalog page alone (`-catalog -catalog-page search`) cut the class from 411 to 113 seconds there, and the tests still check the same controls.
- **Boot a newly created simulator before its first test run.** Twice, `xcodebuild test` on a simulator just made with `simctl create` sat for 20 minutes with an empty test log. `xcrun simctl boot <udid>` then `xcrun simctl bootstatus <udid> -b`, then the test run, worked first time.
- **The local hook:** `.githooks/pre-commit` running `gitleaks git --pre-commit --staged --redact --log-level warn`, installed per clone by a script that sets `core.hooksPath`. Test it with a fake but well-formed token (a random 36-character `ghp_` string trips the `github-pat` rule). AWS's documented example key doesn't work as a test, because gitleaks allowlists it.

## 2. Design system
Tokens, dark mode, Dynamic Type, component catalog, snapshot tests. *(Phase 2)*

Verified 14 October 2026 with Xcode 26.6 (Nifty Outfit Nook, Phase 2a):
- **Keep colour values in one Swift file and test the asset catalog against it.** A `Palette.swift` with every token's light and dark hex lets tests compute WCAG contrast without UIKit. Two tests keep the catalog honest: one decodes each `.colorset/Contents.json` (found through `#filePath`, which simulator tests can read, on CI too) and compares it with the palette; the other resolves the compiled colour through SwiftUI, `Color(name, bundle: .module).resolve(in: env)` with `env.colorScheme` set to `.light` and `.dark`, and compares `linearRed`, `linearGreen`, `linearBlue` and `opacity` with the palette after converting to linear sRGB (tolerance 0.004). Change one channel in a colour set to prove both fail.
- **Xcode generates asset symbols for a package's asset catalog too.** A colour set named `background` gives the module a `ColorResource.background`, so `Color(.background)` becomes ambiguous if your own token enum has a `background` case. Give your initializer a label (`Color(token: .background)`).
- **Main-actor default isolation reaches extensions on SwiftUI types.** With `.defaultIsolation(MainActor.self)`, a `Color` initializer or `static let` added in an extension is main-actor isolated, and a `nonisolated` token struct can't call it. Mark those members `nonisolated`. `Color(_:bundle: .module)` itself is fine to call from them.
- **Check contrast on what's actually under a see-through tint.** Blend the tint over each opaque colour it sits on (both ends of a gradient, the floor) before measuring, and list every pairing the design relies on as data, so the test covers new pairings by adding a line.
- **A shadow that falls only below needs more than `.shadow`.** SwiftUI's shadow has no spread, so CSS like `0 10px 16px -12px` becomes a halo all round. Draw it as a background: the same shape inset by the spread, offset down, blurred by half the CSS blur, and masked with the shape punched out (`ZStack { Rectangle().padding(-n); shape.blendMode(.destinationOut) }.compositingGroup()`) so a see-through fill on top stays clean. It doesn't change layout.
- **Map text roles to Dynamic Type styles and test the default sizes.** `UIFont.preferredFont(forTextStyle:compatibleWith:)` at `.large` gives each style's default size, so a test can hold every role within a couple of points of the mockup. The smallest styles don't shrink below 11 pt at `.extraSmall`, so test growth upward only.
- **System font designs need no licence check.** `.rounded` (SF Pro Rounded) and `.serif` (New York) come with `Font.system(_:design:weight:)` and scale with Dynamic Type. Nothing is bundled.

Verified 14 October 2026 with Xcode 26.6 and swift-snapshot-testing 1.19.6 (Nifty Outfit Nook, Phase 2b):
- **Draw SwiftUI snapshots with `ImageRenderer`, not the library's view strategy.** In a package test target (no host app) `.image(layout:traits:)` renders through `layer.render(in:)`, which drops SwiftUI `.blur`, so soft shadows vanished, and `.sizeThatFits` measured before the AX5 trait applied, so tall layouts were cut off and text truncated. `ImageRenderer` with `proposedSize = ProposedViewSize(width: w, height: nil)`, `scale = 2` and `.environment(\.colorScheme)`, `.dynamicTypeSize`, `.locale` set on the view draws blur and lays out at the real text size. Hand the `UIImage` to `assertSnapshot(of:as: .image(precision:perceptualPrecision:scale:))`. `drawHierarchy` needs a host app.
- **`ImageRenderer` can't draw UIKit-backed views.** `TextField`, `ScrollView`, `ProgressView` and `Toggle` come out as a yellow box with a no-entry sign. Give components an environment flag that swaps in plain SwiftUI that looks the same (a `Text` for the field, a stack for the scroll view), set it only in snapshot tests, and cover the real controls with UI tests. A custom SwiftUI loading indicator avoids the problem for spinners.
- **A sideways scroll view's stand-in must not widen its parent.** A `.fixedSize()` row inside `.frame(maxWidth: .infinity, alignment: .leading)` still reports its full width and pushes the whole snapshot off-centre. A tiny `Layout` that reports the proposed width and places the child at the leading edge fixes it.
- **Snapshots at AX5 find layout bugs fast.** The first recording showed words broken mid-word in buttons, chips and rows. Fixes that held: `ViewThatFits` (icon beside a one-line `fixedSize` title, else icon above a wrapping title), rows that move the icon above the title at accessibility sizes, pairs of buttons that stack at accessibility sizes, and chip bars that wrap instead of scrolling.
- **Same runtime, same pixels.** The iOS 26.5 simulator runtime (build 23F77) on an Apple-silicon Mac and on GitHub's `macos-26` runner produced matching images with a tolerance of `precision: 0.995, perceptualPrecision: 0.98`, and re-recording locally gave byte-identical PNGs. Pin the runtime in the simulator-picking script rather than taking the newest, and add a test that fails with a clear message on any other runtime.
- **Record and artifacts through `xcodebuild`.** Environment variables prefixed `TEST_RUNNER_` reach the test process on the simulator: `TEST_RUNNER_SNAPSHOT_TESTING_RECORD=all` re-records, `TEST_RUNNER_SNAPSHOT_ARTIFACTS=<dir>` collects failed images for a CI upload. Don't put `.snapshots(record:)` on the suite, or it overrides the environment variable.
- **A test-only package still resolves its whole manifest.** swift-snapshot-testing pins swift-custom-dump, xctest-dynamic-overlay and swift-syntax in `Package.resolved` even though the `SnapshotTesting` product builds none of them. List them in the dependency note. With a local package added to the project as a folder, Xcode writes its own `Package.resolved` under `*.xcodeproj/project.xcworkspace/xcshareddata/swiftpm/`, separate from the package's; commit both, check they agree, and build with `-onlyUsePackageVersionsFromResolvedFile`.
- **Prove debug and test code stay out of Release.** After a Release build, `nm` on the app binary for the catalog's and the snapshot library's type names (and `strings` for the launch argument) returns nothing; the same check on the Debug build's `.debug.dylib` finds hundreds of catalog symbols, which shows the check works. Run it in CI.
- **A colour that's close to the background disappears as a fill.** The soft accent (`#EFE6DB`) on the wall (`#F4EEE6`) passed every contrast test as a text background but made icon circles and pressed states invisible. Look at fills on the simulator, not only the numbers.

Verified 14 October 2026 with Xcode 26.6 on the iOS 26.5 simulator (Nifty Outfit Nook, Phase 4, an illustrated Home screen):
- **Multi-colour vector art that follows dark mode: two SVGs per image set.** Template rendering only tints one colour, so for a drawing with dozens of colours give each `.imageset` an Any SVG and a Dark SVG (`"appearances": [{"appearance": "luminosity", "value": "dark"}]`) with `"preserves-vector-representation": true`. Generate both from one source with a script that maps every colour, so the light and dark files only differ in colours, and test that (same text once the hex values are blanked, each dark colour equal to the rule applied to the light one). SVGs with clip paths, linear and radial gradients and `opacity` rendered correctly from a Swift package's asset catalog on the simulator in both appearances, and through `ImageRenderer` in light. We replaced `<use href>` with copies before shipping rather than relying on the system renderer to resolve references.
- **Lay out an illustrated scene from the mockup's own coordinates.** Keep every rect from the design's fixed stage (here 390 x 844) as data, and compute one scale and origin per screen: fit the part of the scene that must show between the bars, never wider than the screen, and never below the scale that keeps the tightest pair of controls 44 pt apart. Grow each tap area to 44 x 44 around its object. Pure layout code makes it testable without UI: for each phone size, check every target is 44 pt or more, no two targets overlap, and none sits under the bars. Where the phone is too short (iPhone SE), let the scene scroll a little rather than shrink targets.
- **Bar heights in iOS 26** from `GeometryReader`'s `safeAreaInsets` inside `NavigationStack` in a `TabView`, inline title: 116 pt top and 83 pt bottom on iPhone 17 and 17 Pro Max, 74 and 83 on iPhone SE (3rd generation). Put the scene in a `ScrollView` with `.ignoresSafeArea()` and place content using those insets; the wall and floor then run under both bars, and `scrollDisabled` keeps it still when it fits.
- **A shrinking `Text` next to a `Spacer` gets squeezed and truncates instead of shrinking.** "Closet" with `minimumScaleFactor(0.5)` in an `HStack` with icons and a `Spacer(minLength: 0)` came out as "Clo…" at a slightly smaller width; `layoutPriority(1)` didn't fix it. `ViewThatFits(in: .horizontal)` over full, shorter and text-only versions, each with a `.fixedSize()` title, did.
- **Fixed-size labels on art need a Dynamic Type cap until the large-text layout exists.** At AX5 the icons and two-line plates overflowed their drawn spaces. `.dynamicTypeSize(...DynamicTypeSize.xxxLarge)` on the scene kept everything inside; the accessibility sizes then need their own layout rather than a bigger scene.
- **Small gotchas.** A command-line `xcodebuild` doesn't add new strings to a package's String Catalog, so add the entries yourself, with plural variations for counts ("1 piece", "17 pieces"), and test a count of one. swift-snapshot-testing writes `__Snapshots__` next to the test file, so a test in `Tests/X/Home/` needs `exclude: ["Home/__Snapshots__"]`. A test target can load the module's assets with `UIImage(named:in: .module, compatibleWith:)` through `@testable import`.

Verified 14 October 2026 with Xcode 26.6 on the iOS 26.5 simulator (Nifty Outfit Nook, Phase 5a, weather, laundry and a pet in the illustrated Home):
- **`ImageRenderer` picks the Dark image from the environment.** With `.environment(\.colorScheme, .dark)` on part of the view, asset-catalog images with a Dark appearance rendered their dark SVG. So one snapshot can stack every state of a drawing in light above dark, which kept six windows and four hampers to two images.
- **Reduce Motion can't be set in a test, so pass `animates` in.** `EnvironmentValues.accessibilityReduceMotion` is get-only. A small animated view that takes `animates: Bool` (false under Reduce Motion, and false from a custom environment flag the snapshot tests set) draws a fixed resting frame; when it's true, a `TimelineView(.animation(minimumInterval: 1.0 / 15))` drives a pure `drift(at: time)` function, which unit tests can check. A slow drift of a point or two needs no more than 15 frames a second. Re-running the suite gave matching snapshots.
- **`accessibilityIdentifier` on a plain container renames everything inside it.** A sheet's `VStack` with an identifier replaced its buttons' own identifiers, and the UI test couldn't find `laundryTracking.turnOn`. Put identifiers on the elements, not their stacks. A `ScrollView` with an identifier didn't do this to its rows.
- **Recolouring art into a neutral palette: keep the hue where it carries meaning.** Mapping every blue to warm stone made a sunny and a cloudy window look alike. Letting the windows' blues keep their hue at 40% of their colour kept each weather readable and still quiet. Things that stand for something real (her clothes, her dog) keep their own colours in light and take the room's dimming in dark. Derived states (a faded "off" version) are best generated from the base drawing by the same script, with a test that the shapes match.
- **One launch argument still scales.** `-fixtures demo:weather=snow:laundry=full` (options after colons, in any order, unknown ones ignored) forced every window and hamper state for UI tests and by-eye checks without new flags.

Verified 14 October 2026 with Xcode 26.6 on the iOS 26.5 simulator (Nifty Outfit Nook, Phase 5b, large-text, sideways and dark variants of an illustrated Home):
- **Switch whole layouts inside one screen, not between screens.** A small enum chosen from `dynamicTypeSize.isAccessibilitySize` (any AX size, in any orientation) and then `verticalSizeClass == .compact` (a phone held sideways) picks which view the screen's `NavigationStack` shows. The model, the navigation path and an open sheet live in the screen, so rotating or changing the text size keeps whatever is open; a UI test that opens a pushed screen sideways and turns the phone upright proves it. Give each control the same accessibility identifier in every layout so the same UI test helpers work in all of them.
- **iOS 26 safe area for iPhone 17 held sideways** (inside `NavigationStack` in a `TabView`, navigation bar hidden): 0 at the top, 62 pt at each side and 64 pt at the bottom for the tab bar. Scale an illustrated scene to the height between them and let the controls column keep a minimum width. A ScrollView for that column with `.contentMargins(.bottom, inset, for: .scrollContent)` keeps the last control above the floating tab bar when big text makes it scroll.
- **A cramped sideways scene can keep its drawings tappable if the real controls sit beside it.** Make the drawings tappable but hidden from VoiceOver, and put the same controls next to them as tiles with words and 44 pt targets, so nothing is read twice and small drawers are never the only way in. A short visible word with a longer spoken name ("Feedback" for "Send feedback") gets `accessibilityInputLabels([short, full])` so Voice Control answers to both.
- **At AX4 and AX5 move a row's icon above its words.** With a fixed icon column, single words like "Occasion" broke mid-word ("Occa-sion") at AX5 on a 402-point phone. AX3 still fit with the icon beside. Give the icon column a fixed width, or the words don't line up from row to row.
- **UI tests at a given text size and orientation.** Launch with `-UIPreferredContentSizeCategoryName UICTContentSizeCategoryAccessibilityXXXL` (AX5; `...AccessibilityXL` is AX3), and set `XCUIDevice.shared.orientation`. The orientation stays on the simulator after the test ends, so reset it: `tearDown` isn't main-actor isolated, but `addTeardownBlock { @MainActor in XCUIDevice.shared.orientation = .portrait }` works. The same persistence is handy for checking a sideways layout by eye on a simulator that has no window: run a one-line test that rotates it, then `simctl launch` and `simctl io screenshot` (the PNG comes out in portrait framing; rotate it to look).
- **`ImageRenderer` with no proposed height can lay a tall page out shorter than it measured.** A scrolling page drawn as a plain stack came out with transparent bands above and below and its last rows squeezed over each other, while the simulator drew it correctly. `.fixedSize(horizontal: false, vertical: true)` on the view before rendering matched the simulator. Also measure the simulator's own safe area once and pass it in, since a still image has none.
- **Check derived art in dark on its own.** A "tracking off" hamper made by fading the light drawing, then put through the dark rule, became the brightest thing on the dark floor: the opposite of quiet. Give derived states their own dark rule (here the mockup's darker filter, ending dimmer and greyer than the lit version) and a test that it stays darker on average. A radial glow with a fixed end radius, clipped to a circle, showed a hard edge once its frame got smaller; set the end radius from the frame.

Verified 14 October 2026 with Xcode 26.6 on the iOS 26.5 simulator (Nifty Outfit Nook, Phase 6, a searchable grid of 2,400 garments):
- **Work out each cell's details once, when the data loads.** Suitcase names per garment, the dirty flag and the last-worn date went into a small value per item, with a dictionary by ID; filtering then maps matches back to those values. In Debug on the simulator, preparing 2,400 items took 48 ms and the slowest filter or search change 7 ms, so filtering on the main actor was fine. Keep spoken strings out of that step: building VoiceOver text in the cell's body only costs for the cells on screen.
- **Debounce search with a cancellable task, and give tests a way to wait.** Each keystroke cancels the last `Task { try? await Task.sleep(for: delay); guard !Task.isCancelled ... }`. A `settleSearch()` that awaits the pending task, plus a counter of searches applied, let a test type four letters, see nothing run, settle, and see exactly one search. Apply at once when the field is emptied or Search is pressed.

## 3. Models and mock data

Verified 14 October 2026 with Xcode 26.6 and Swift 6.3 (Nifty Outfit Nook, Phase 3):
- **Split the package three ways.** Models holds value types, rules as pure functions and service protocols, with Foundation only and no user-facing strings (enum cases are words; screens localize them). Fixtures holds actor stores and sample data and depends on Models. Features depends on Models only, and the app target is the one place that builds concrete services. A `NookServices` struct of `any Protocol` values goes into the SwiftUI environment with `@Entry var services: NookServices?`; that compiles cleanly in a module with `defaultIsolation(MainActor.self)`.
- **Stores keep data; rules decide.** Stores return everything they hold and the screens filter with pure functions (eligibility, repeat window, favourites, filters). Every rule takes `now` and a `Calendar` as parameters, tests pin a UTC Gregorian calendar and a fixed date, and fixture dates are generated relative to `now` so the running app reads naturally.
- **Typed throws work across async protocols and actors.** `func garments() async throws(StoreError) -> [Garment]` in a protocol, implemented by an actor, compiles under complete strict concurrency. `Task.sleep` throws an untyped error, so wrap it in `do`/`catch` and throw your own `.cancelled`. Keep "couldn't finish" as a thrown error and "the data doesn't allow it" as an outcome case, so a network failure can never be shown as a small closet.
- **One launch argument for set and behaviour.** `-fixtures demo:offline` (also `slow`, `stylist-fails`, `stylist-partial`, `stores-fail`) gives UI tests every loading, error and offline state without extra flags. Unknown parts fall back to the defaults.
- **A generated large data set should own its arithmetic.** A SplitMix64 generator with its own `int(in:)` (modulo) and `unit()` makes the 2,400-garment closet identical on every run without relying on how the standard library picks random integers. Make dates per record unique by drawing day offsets into a `Set`, and never generate a wear date before the record was added (a test checks both).
- **Performance tests: measure serially, bound loosely.** Swift Testing runs tests in parallel, so record numbers with `-parallel-testing-enabled NO`. In Debug on the simulator, generating 2,400 garments took 36 ms, five filters 35 ms and one mock styling 41 ms; the tests allow 1 s or 500 ms, so they catch big regressions without flaking on CI. Later, two of these checks failed once on a busy CI runner (a context build that takes 6 ms locally took 862 ms there), because the snapshot suites were running alongside. Taking the fastest of three runs, and allowing three times the bound when `CI` is set (pass it to the simulator as `TEST_RUNNER_NOOK_CI`, which xcodebuild hands to the tests without the prefix), keeps them meaningful without the flake (Phase 8a).
- **Swift Testing gotcha:** `#expect(items.contains(where: \.isArchived))` failed to compile inside the macro expansion ("call can throw, but it is not marked with 'try'"). Use a closure, `#expect(items.contains { $0.isArchived })`.
- **UI test gotchas.** A text with its own `accessibilityIdentifier` inside a `ContentUnavailableView` that also had an identifier wasn't found by that identifier; matching the label (`staticTexts["17 pieces in the sample closet"]`, or a `label ENDSWITH` predicate) worked. Numbers in labels are formatted for the locale ("2,117"), so strip non-digits before comparing.
- **Watch CI time as UI tests grow.** Locally, two extra UI tests with five app launches added about 45 seconds. On `macos-26` the `build-and-test` job then took 8.5 to 13.5 minutes across three runs, against 5 to 7 before. Keep launches few and cover data paths in package tests.

Verified 15 October 2026 with Xcode 26.6 on the iOS 26.5 simulator (Nifty Outfit Nook, Phase 15a):

Rotate with `XCUIDevice.shared.orientation`.
- **One drawing, several arrangements.** For an illustrated screen that needs a wide and a tall composition, keep every rect in a plan struct and build the new plans by moving whole groups (a piece of furniture with its labels and tap area) to a new corner and scaling around it, as CSS `transform: scale()` does. Labels can't drift off their drawings, and a test can check every control stays 44 points or more and apart from its neighbours in every plan and window.
- **Bars on iPad.** With the bottom tab bar, the iPad Pro 11-inch has 86 points at the top and 77 at the bottom, in both orientations.
- **iPad UI tests on CI without a new runner.** A second `scripts/test.sh` step in an existing UI job, on an iPad simulator, reuses the job's checkout and toolchain and stays within the free plan's five macOS runners. It took 12 minutes on the hosted runner for about 6 minutes of tests (the rest was the iPad simulator's boot and first launch), so add it to the lightest part. The hosted runner's iOS 26.5 iPad simulator had Windowed Apps on, so window resizing worked there too.
- **iPad snapshots at 1x.** A whole 13-inch window at 2x is several megabytes per image; 1x with the same tolerances still catches a moved drawing or changed text.

Verified 15 October 2026 with Xcode 26.6 on the iOS 26.5 simulator (Nifty Outfit Nook, Phase 15b):
- **Two panes or one column, chosen in a still image too.** `ViewThatFits(in: .horizontal) { sideBySide.frame(minWidth: 720, idealWidth: 720, maxWidth: 1120); stacked }` picks the panes only when the page offers 720 points, and `ImageRenderer` makes the same choice the screen does, so snapshot tests need no width passed in. Let each pane's content know which branch it's in (a closure parameter) so a picture can grow beside its controls, and keep the stacked branch the same views with the same spacing as the old phone column, so phone snapshots don't change.
- **A form sheet that fits its content on iPad.** `.presentationSizing(.form.fitted(horizontal: false, vertical: true))` did nothing while `.presentationDetents` was also set; set detents only over a compact window. Read the width class in a `ViewModifier` around `.sheet`, from the view that presents it, not inside the sheet. A `ScrollView` has no height to offer, so measure the content with `onGeometryChange` and give the scroll view `.frame(idealHeight:)`.
- **Measure only on screen.** `onGeometryChange` writing to `@State` inside a view drawn by `ImageRenderer` changed three still images whose content held lazy grids (the height came out a few points short). Attach the measuring only in the on-screen branch.
- **Keep `withAnimation` to the control that needs it.** A segmented switch that set its value inside `withAnimation` animated the whole page it changed. With a detail view swapping beside a grid, SwiftUI drew that change on its own render thread (`com.apple.SwiftUI.AsyncRenderer`) and called the switch's `ForEach` content there; in Swift 6 the main-actor check stopped the app (`EXC_BREAKPOINT` in `_dispatch_assert_queue_fail`, under `swift_task_isCurrentExecutor`). Setting the value plainly and animating only the pill with `.animation(_:value:)` ended it. A crash report in `~/Library/Logs/DiagnosticReports` names the thread and the closure.
- **A scratch UI test is a cheap way to look at every screen.** A test that's never committed walks the app in one orientation and window width (both from `TEST_RUNNER_` variables), saves `XCUIScreen.main.screenshot()` to a folder for each screen, and resizes the window as above. It found the crash above, which the committed tests hadn't reached. Landscape screenshots sometimes come out rotated; the content is still right.

Verified 15 October 2026 with Xcode 26.6 on the iOS 26.5 simulator (Nifty Outfit Nook, Phase 16a, coach marks):
- **A coach-mark overlay over a whole tab app.** Keep one observable tour controller above the `TabView` and draw the overlay there, so the dim covers the bars and the tab bar can't be tapped through it. Each target view reports `frame(in: .global)` through `onGeometryChange` into the controller, keyed by an anchor ID and the view's own owner token (so a layout leaving doesn't remove the anchor the next layout just registered). The overlay subtracts its own global origin. The spotlight then followed its target through rotation, an iPad window dragged to a third of the screen and back, Dynamic Type layouts and scrolling, with no extra code.
- **Measure before `.position`.** A view placed with `.frame(...).position(...)` fills its parent, so a geometry reader or anchor after `.position` measures the whole canvas. Attach it between `.frame` and `.position`.
- **Place a popover card in a custom `Layout`.** The card's height depends on its words and the text size, so a `Layout` measures it (`sizeThatFits` with a nil height), picks the side, and places the spotlight, the tail and the card in one pass. `ImageRenderer` then draws the same placement as the screen, and the snapshot tests pass the target rect straight in. Parts that aren't shown (no spotlight, no tail) are placed far off screen.
- **Accessibility order followed drawing order, not `accessibilitySortPriority`.** In an overlay with a card and an invisible button over the highlighted control, the button came first however the priorities or the `Layout`'s subview order were set. Drawing the button after the card (`.zIndex(2)` over the card's `.zIndex(1)`; `zIndex` works in a custom `Layout`) put the card first. They never overlap, so the drawing order changes nothing visible.
- **Check accessibility order from `debugDescription`, not a query.** XCUITest queries (`firstMatch`, `allElementsBoundByIndex`) return elements breadth first, so a button one level up beats the text inside a card. The printed tree is in the order the app exposes; compare the positions of the identifiers in it. A SwiftUI view with `.accessibilityAddTraits(.isModal)` shows up there as an `Alert`, a handy check that the modal trait is applied. `.accessibilityHidden(true)` on a `TabView` did not remove the screens under it from XCUITest's tree, so test "nothing under the overlay" with `isHittable` instead.
- **A soft cut-out in a dim:** draw the dim, then a blurred rounded rectangle with `.blendMode(.destinationOut)`, inside `.compositingGroup()`. It renders the same in `ImageRenderer`.
- **Escape can't be tested from XCUITest on the iOS 26.5 iPhone simulator.** `app.typeKey(XCUIKeyboardKey.escape, modifierFlags: [])` reached neither `.keyboardShortcut(.cancelAction)` nor `.onKeyPress(.escape)` on a focused view (15b saw the same on iPad). Route Escape and the VoiceOver escape action to the same function the Skip button calls, unit-test that function, and list Escape for a device check.
- **Let a card's words scroll and keep its buttons.** `VStack { ViewThatFits(in: .vertical) { words; ScrollView { words } }; buttons.layoutPriority(1) }` keeps the buttons on screen at AX5 while the words scroll. The still-image stand-in for the scroll view must be able to shrink (`.frame(minHeight: 0, maxHeight: .infinity, alignment: .top).clipped()`), or the snapshot shows the card running off the screen.
- **Don't start a modal overlay while a toast is up.** VoiceOver stays inside a modal overlay, so a toast under it wouldn't be read. Start the overlay when the toast's binding goes back to `nil`.
- **Swift Testing's `#expect` can't take a `mutating` call** on a local (`#expect(run.next() == .moved)` fails to compile: `$0` is immutable). Call it first, then expect on the result.

## 6. Privacy and security baseline

Verified 15 October 2026 with Xcode 26.6 on the iOS 26.5 simulator (Nifty Outfit Nook, Phase 14a):
- **Check the app switcher's snapshot on the simulator by reading the file iOS keeps.** After pressing Home (`XCUIDevice.shared.press(.home)` in a throwaway UI test), the snapshot is in the app's data container (`xcrun simctl get_app_container <udid> <bundle id> data`) under `Library/SplashBoard/Snapshots/sceneID:<bundle id>-…/`, as `.ktx` files in light and dark. `sips -s format png <file> --out <png>` converts them. Only the latest state is kept, so check one state per run. This is how we confirmed that a cover shown while `scenePhase != .active` is what iOS keeps.
- **A cover over a scrolling screen must run under the bars.** The first check showed the measurements' section header and the units switch through the iOS 26 navigation bar's blur: the overlay sat inside the safe area while the scroll view's content ran under the bar. `.ignoresSafeArea()` on the cover fixed it.
- **Make a Sensitive value type unprintable.** `CustomStringConvertible` and `CustomDebugStringConvertible` returning "redacted" plus `CustomReflectable` with no children means `print`, string interpolation, `String(reflecting:)` and `dump` show no values. A unit test checks each one, so a later log line can't leak body measurements by accident.

Verified 15 October 2026 with Xcode 26.6 on the iOS 26.5 simulator (Nifty Outfit Nook, Phase 14b, Delete my data before accounts exist):
- **Make every store erasable through its protocol, and report deletion part by part.** An `ErasableStore` protocol (`eraseAll()`) that every store protocol refines, and a `DataDeletionService` that erases each part, keeps going past a failure and returns deleted, pending or failed per part, let the whole flow be built and tested on in-memory stores. A test fills every store, deletes, and checks that each reads the same as the empty fixture set; `stores-fail` shows the "what's left" state. Accounts and server data later become new parts whose outcome can be pending, without changing the screen.
- **After deleting, rebuild the whole tab tree instead of reloading each screen.** The root view puts its tabs, their navigation paths, the image caches and any unsent drafts in one child view and gives it `.id(generation)`; bumping the number after a complete deletion throws every screen away, so nothing from before can show on a screen that was already open. A UI test deletes from a pushed screen and finds a fresh Home with the Home tab selected and an empty Closet.

## 8. Photos and image handling

Verified 14 October 2026 with Xcode 26.6, the iOS 26.5 and 27.0 simulators and macOS 26.5 (Nifty Outfit Nook, Phase 8a, subject lifting):
- **Vision's foreground mask can't be trusted on the iOS simulator, and it fails differently by host.** On an Apple-silicon Mac, `VNGenerateForegroundInstanceMaskRequest` fails with Vision error 9 (`internalError`, "Could not create inference context") on both runtimes; `supportedComputeStageDevices` lists only the simulator GPU, so there's no CPU device to switch to. On GitHub's `macos-26` runner the same request ran without an error and found no subject in a plain flat lay, so mapping the local error wasn't enough and CI failed. Under `#if targetEnvironment(simulator)` return a typed `unsupported` before calling Vision (after validating the input), skip the tests that need a real mask with Swift Testing's `.enabled("reason") { await probe() }` (one cached `Task` that tries a single cutout), and compile the device path with `xcodebuild build -destination generic/platform=iOS CODE_SIGNING_ALLOWED=NO`. The request does run on macOS, so a throwaway command-line harness built from the same source files gives real Mac numbers.
- **Make a new `VNImageRequestHandler` for every measurement.** Performing the same request on the same handler again returns the cached result in well under a millisecond, which makes warm timings meaningless.
- **Vision's masks are a fixed square, not the photo's shape.** The instance mask is 512 x 512 `OneComponent8` labels (0 is background) stretched over the whole image, so pixel fractions give coverage and normalized bounds directly. `generateMask(forInstances:)` is also 512 x 512 and held only 0 and 1 in our tests; the soft edges show in the full-size outputs. `generateMaskedImage(..., croppedToInstancesExtent: true)` returns premultiplied 32BGRA, which wraps straight into a `CGImage` (`byteOrder32Little | premultipliedFirst`). Read edge softness from its alpha with `vImageHistogramCalculation_ARGB8888`.
- **Downsample with ImageIO and keep the working size at or under half the photo.** `CGImageSourceCreateThumbnailAtIndex` with `ThumbnailWithTransform` applies the EXIF orientation and doesn't enlarge small photos. For a 4,032 x 3,024 JPEG on an M1 Max, 1,536 px took about 30 ms to decode and 2,048 px 85 ms or more: up to 2,016 the decoder can halve while decoding, above it decodes at full size. Check the pixel count from the image properties before decoding, to refuse huge files.
- **`PhotosPicker` needs no permission and no Info.plist key on iOS 26.** It opened with no prompt in an app with no `NSPhotoLibraryUsageDescription`, and showed "Private Access to Photos". It also says "Location Is Included" by default, so picked photo data can carry GPS. Strip metadata yourself: a PNG written from pixels with `CGImageDestinationAddImage(destination, image, nil)` has no EXIF, GPS or TIFF dictionary, and a test can check that with a JPEG that has a made-up location. Ask for `preferredItemEncoding: .current` to get the stored HEIC without a conversion.
- **Measure memory with `task_info(TASK_VM_INFO)`.** `phys_footprint` is what iOS counts against the app's limit; sample it every few milliseconds from a detached task while the work runs, and keep the maximum. `os_proc_available_memory()` returns 0 on the simulator, so treat 0 as "not reported".

Verified 14 October 2026 with Xcode 26.6 on the iOS 26.5 simulator (Nifty Outfit Nook, Phase 8b, sticker outlines and a photo tile fallback):
- **Draw a sticker edge with a greyscale dilation, not offset copies.** The CSS trick (eight `drop-shadow`s in a ring) leaves gaps beside thin straps and notches at corners. `vImageDilate_Planar8` on the cutout's alpha with a round brush does it properly: for 8-bit it takes `max(source − brush)` over the brush with saturation, so a brush of 0 inside the radius rising to 255 over its last pixel gives a soft round edge, and the garment's anti-aliasing carries through, so slanted sides stay smooth. Double the alpha first (`vImageTableLookUp_Planar8`), or a thin strap whose pixels are only partly covered gets see-through paper. A 640 x 800 dilation with a 27-pixel brush took 7 ms in Debug; a pure-Swift exact distance transform, run at twice the resolution to smooth the edge, took 1.7 s in Debug for one detail-sized sticker (at the picture's own resolution its binary mask made the edge step a pixel at a time on slants). Hot pixel loops in Swift crawl without optimisation, and package tests run in Debug, so reach for Accelerate.
- **Bake the shadow into the cached sticker, below only.** `CGContext.setShadow` while drawing the white silhouette, with the offset at least as large as the blur, left no shadow above the sticker (a test checks the rows above are clear), and the cached picture costs nothing per frame to scroll. Size the edge and shadow from the sticker's long side: one width everywhere looks heavy on small stickers and thin on big ones.
- **Make each sticker once, off the main actor, keyed by what it shows.** A detail-sized sticker at 3x took about 25 ms in Debug. A main-actor cache with an in-flight task per key (two views asking at once share one render), a byte budget with least-recently-used eviction, and a clear on memory warning kept it to one render per picture, size, scale and appearance. Key a placeholder drawing by its kind and colours, and a 2,400-piece closet needs a few hundred stickers, not 2,400. Key a photo cutout by its picture reference rather than the garment ID, so a new photo can't show a stale sticker.
- **A fallback should take exactly the sticker's space.** The photo tile fills the same frame the sticker fits into, so a piece that falls back never moves the layout; cropping the photo to the cutout step's subject bounds (plus a margin) keeps the garment in view.
- **`.task` never runs on a view with nothing in it.** A picture view whose body was an `if` that drew nothing while it waited for its photo had `.task(id:)` on the empty result, and the load never started: the screen stayed blank in the app, while snapshot tests (which skip loading) looked fine. A `ZStack { Color.clear; content }` under the modifier fixed it. Look at the screen in the simulator, not only the snapshots.
- **Swift Testing gotchas.** `@Test(arguments:)` with a list of tuples of more than two values didn't compile ("no exact matches in call to macro 'Test'"); pass one value and switch on it. A `#require` nested inside another `#require` failed with "recursive expansion of macro"; unwrap in two steps.
